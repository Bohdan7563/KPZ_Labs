# ADR-001: Перехід від Anemic Domain Model до Rich Domain Model (Бібліотека)

## Статус
Прийнято (Accepted)

## Контекст
У початковому коді весь бізнес-процес видачі книги (розрахунок застави, комісії, зміна статусу) був зосереджений в одному монолітному класі `LegacyLibraryProcessor`. Сутності `Reader`, `Book`, `LoanRecord` були просто "мішками з даними" (Anemic Domain Model) з публічними полями. Це порушувало принципи інкапсуляції та призводило до високого зчеплення (High Coupling). Крім того, розрахунок комісій містив процедурні розгалуження `if-else` залежно від категорії книги.

## Рішення
Згідно з патернами GRASP:
1. **Information Expert:** Логіку розрахунку застави та комісії перенесено безпосередньо в сутність `LoanRecord`, яка володіє всіма необхідними даними.
2. **Polymorphism + Protected Variations:** Замінено `if-else` на поліморфну ієрархію інтерфейсу `BookCategory` (`Standard`, `Academic`, `Rare`).
3. **Creator:** Створення об'єкта `LoanRecord` винесено у статичний фабричний метод, який гарантує валідність стану.
4. **Pure Fabrication + Indirection:** Створено штучні класи `LoanRepository` (для збереження) та `NotificationService` (для відправки листів), щоб розвантажити домен.

## Наслідки
**Позитивні:**
* Висока згуртованість (High Cohesion): `LoanRecord` тепер відповідає лише за свою логіку.
* Низьке зчеплення (Low Coupling): Контролер більше не залежить від деталей збереження.
* Легке розширення: для додавання нової категорії книги достатньо створити новий клас, що реалізує `BookCategory`.
